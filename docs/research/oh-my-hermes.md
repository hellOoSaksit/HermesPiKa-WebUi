# วิเคราะห์ oh-my-hermes (OMH) เทียบกับ HPK

> อ่านโค้ดอย่างเดียว ไม่ได้รันอะไร · v4.0.8 · สัญญาอนุญาต MIT
> **กฎของเรายังเหมือนเดิม:** เอาเฉพาะ *ไอเดีย* มาเขียนเองใหม่หมด ไม่คัดลอกโค้ด ไม่เรียก API ของเขา

## 1. เขาคืออะไร

OMH เป็นชั้นเสริมบน Hermes Agent โดยไม่แก้โค้ด Hermes เลย มีสามส่วน:

- **Hermes plugin:** มี tool 28 ตัว (`omh_dag`, `omh_delegate_route`, `omh_memory` ฯลฯ) และ hook 12 จุด เช่น `pre_tool_call`, `subagent_start/stop` และ `pre_gateway_dispatch`
- **Skill มากกว่า 150 ตัว:** เป็นไฟล์ `SKILL.md` ที่สร้างจาก catalog ใน Python และลงทะเบียนผ่าน `skills.external_dirs`
- **UI:** มี TUI (Python ล้วนประมาณ 40k บรรทัด) และแอปเดสก์ท็อป omher (Tauri + React 19) ที่คุยกับ Python bridge ผ่าน WebSocket

ขนาดรวม: Python ประมาณ 600k บรรทัด, ไฟล์เทสต์ 1,253 ไฟล์, repo 143 MB และ CHANGELOG 16.5k บรรทัด

## 2. ระบบ: จุดที่น่าเรียนรู้

| เรื่อง | เขาทำอย่างไร | ข้อสังเกต |
|---|---|---|
| **`/dag-ulw` กราฟงาน** | parent วางกราฟสูงสุด 48 node โดยแต่ละ node มี category, prompt, `depends_on`, `write_scope` และ role (build/verify/review) จากนั้นรัน node ที่พร้อมแบบขนานผ่าน `delegate_task` | node แยกสำหรับ **verify** ต้องรันคำสั่งจริง แล้วรายงานผลทีละ criterion |
| **กัน write ชนกัน** | ตอน define จะปฏิเสธ node ที่รันพร้อมกันได้แต่ scope ทับกัน ตอนรัน `pre_tool_call` จะบล็อกการเขียนนอก scope | **ไม่ตรวจคำสั่ง shell** ซึ่งเขายอมรับเองว่ากันได้ไม่หมด |
| **ซ่อมเมื่อพัง** | ซ่อมได้ไม่เกิน 2 รอบต่อ node และขยายงานได้ไม่เกิน 2 รอบต่อ run โดย node ที่พังจะบล็อกเฉพาะ node ที่ขึ้นกับมัน | |
| **เลือกโมเดลตามประเภทงาน** | มี 18 category (ultrabrain, deep, quick, visual-engineering, review…) แต่ละ category มี chain ของโมเดลพร้อม effort ถ้า provider ปฏิเสธจะเลื่อนไปโมเดลถัดไปเอง | เขียนทับ `delegation.model` ใน config.yaml **ทุกตา** แล้วค่อยคืนค่า ซึ่งเปราะ |
| **หลักฐานก่อนบอกว่าเสร็จ** | สถานะประกอบจาก ขั้น · ความมั่นใจ เช่น `Plan · not run`, `Code · reported done`, `Test · verified` | ไอเดียดีมาก ทำให้ "agent บอกว่าเสร็จ" ไม่ถูกนับเป็น "ตรวจแล้ว" |
| **ความจำ** | ทุกข้อเท็จจริงถูก *จำ / ปฏิเสธ / เลื่อน* พร้อมเหตุผลที่เขียนไว้ ความลับ, log และ transcript ถูกปฏิเสธเสมอ ก่อนส่งให้แชทจะจัดลำดับ recall pack และตัดให้ไม่เกิน 9,000 ตัวอักษร | |
| **ความปลอดภัย** | approval tier มีสามระดับ (auto / confirm / refuse) และงานที่ไม่รู้จักจะถูก refuse มี spend gate ที่ต้องพิมพ์ยืนยัน ถ้าไม่รู้ราคาจะแสดง `unknown` ไม่แสดง `$0` | |
| **ทีม** | **ไม่มีเลย** ไม่มี server หลายคน และ "team" ของเขาหมายถึง AI ช่วยงานใน session เดียว | ตรงนี้คือช่องว่างใหญ่ที่เราเหนือกว่า |

## 3. UI: จุดที่น่าเรียนรู้

แอป omher มีเลย์เอาต์สามคอลัมน์: sidebar · แชท · แผงขวา (Details/Terminal/Schedule/Worktrees/Diff/**Plans**)

- **กราฟแผนในแผงขวา:**
  - กล่องเป็นเส้นขอบบาง มีแถบสถานะ 2px ด้านซ้าย
  - ในกล่องแสดง *ชื่องาน · โลโก้โมเดล · effort · category* และสถานะเป็นคำ (Running / waits on 2)
  - ใต้กราฟเป็นรายการ Dependencies แบบข้อความ
- **หัวแผน:** เขียนเป็นประโยคบรรทัดเดียว เช่น "● Running · 2 of 6 done · 1 waiting · 9m · 1 needs you" โดยไม่ใช้การ์ดหรือ progress bar
- **NodeDrawer:** บอกว่าเป็นความพยายามครั้งที่ k จาก n ทำไมถึงเลือกโมเดลนี้ และมีปุ่มเดียวที่แค่เติมข้อความลงช่องพิมพ์โดยไม่ส่ง
- **Activity ย่อ:** แสดง "Worked for 2m 41s · 6 steps" โดย tool call ไม่ได้แถวของตัวเองในไทม์ไลน์
- **คิวการ steer:**
  - ข้อความที่พิมพ์ระหว่างที่ agent ทำงานจะถูกพักไว้ แล้วเลือกได้ว่า Send now / Steer / Edit / Delete
  - ถ้า agent ไม่ได้อ่าน steer นั้นก่อนหยุด จะติดป้าย "not used"
- **Approvals:**
  - ปุ่ม 1/2/3 = ปฏิเสธ / อนุญาตครั้งเดียว / อนุญาตทั้ง session
  - ตอบแล้วการ์ดยุบเหลือบรรทัดเดียว และกด ⌘J เพื่อกระโดดไปคำขอถัดไป
  - ใน TUI คำสั่ง shell ที่ต่อกันจะถูก **แยกทีละคำสั่งพร้อมระบุความเสี่ยง**
- **แถบ Needs you:** ปักไว้บนสุดของ sidebar เป็นบรรทัดเดียว และกางดูรายการได้
- **ตัวเลือกโมเดล:** เป็น pill เดียว (โมเดล | reasoning) ที่มีช่องค้นหา ถ้า gateway ปฏิเสธจะคงค่าเดิมไว้และบอกหนึ่งบรรทัด

**จุดอ่อนของ UI เขา:**

1. **แผน, subagent card และ Plans อ่านได้อย่างเดียว:** สั่ง retry, cancel หรือ steer sub-task จากแอปไม่ได้ ต้องไปทำใน TUI
2. **Sidebar รก:** bots, threads, sessions ที่ซ่อนไว้แต่ยังมีโค้ด, tasks, automations, plugins, dock และวงแหวน usage แย่งที่กันหมด
3. **ผู้ใช้ต้องจำ prefix workflow 10 ตัว** (`ulw-plan`, `ulw-work`, `dag-ulw`…) ก่อนจะใช้งานได้ดี
4. **ต้องติดตั้งแอปเดสก์ท็อป** จึงใช้บน server หรือแชร์ให้ทีมไม่ได้

## 4. เราเหนือกว่าตรงไหนอยู่แล้ว

| | OMH | HPK |
|---|---|---|
| ทีม / server | ไม่มี | `hpk serve` มีโหมดทีม, BOARD claim และแจ้งเตือนงานซ้ำข้ามคน |
| ความลับของโปรเจค | ไม่มีแนวคิดนี้ | privacy shared/private/isolated |
| เส้นแดง | มี approval tier | มีเส้นแดงที่ทุกโหมดข้ามไม่ได้ และรวมเส้นแดงจาก Process→Profile→Project |
| ขนาดและการติดตั้ง | Python 600k บรรทัด + Node + Tauri | Go binary ไฟล์เดียว และเว็บ UI ไม่ต้องติดตั้ง |
| ความรู้ | memory ส่วนตัว | wiki ต่อโปรเจค ถามผู้ใช้ก่อนเสมอ |
| วิธีใช้ | ต้องจำ prefix | แชทเดียว agent แตกงานเอง |

## 5. ข้อเสนอ: เอาไอเดียมาทำให้ดีกว่าเขา

เรียงจากคุ้มที่สุดไปน้อยที่สุด:

1. **แผนงานในแชทหลักที่สั่งงานได้จริง** (เขาทำได้แค่อ่าน)
   - เพิ่มแผง "แผน" ในแชทหลักที่ใช้ track diagram ของเรา
   - แต่ละ sub-task แสดง *โมเดล · effort · ประเภทงาน · ขึ้นกับอะไร*
   - คลิกแล้วทำได้ **steer / หยุด / ลองใหม่ / เปลี่ยนโมเดล** ทันที โดยการเปลี่ยนโมเดลยังเป็นเส้นแดง
   - หัวแผนเป็นประโยคเดียวแบบเขา
2. **สถานะแบบหลักฐาน:** ใช้ `ขั้น · ความมั่นใจ` กับ sub-task, summary card และ Overview เพื่อแยก "agent บอกว่าเสร็จ" ออกจาก "เทสต์ผ่านจริง"
   - sub-task จะ merge เข้าแชทหลักได้ก็ต่อเมื่อเป็น `verified` เท่านั้น
3. **sub-task ตรวจงานแยกอัตโนมัติ:** ตอน `/split` ให้ agent สร้าง sub-task "ตรวจเป้าหมาย" ปิดท้ายเสมอ ซึ่งรันเทสต์จริงและรายงานผลทีละเกณฑ์ ถ้าไม่ผ่านให้ซ่อมได้ไม่เกิน 2 รอบ
4. **write scope กันชนแบบครบกว่าเขา**
   - sub-task ประกาศ scope ไฟล์ตอนแตกงาน แล้ว**ผูกกับ BOARD claim** เพื่อกันชนข้ามคนในทีมด้วย ซึ่งเขาทำไม่ได้
   - เรามี worktree แยกต่อ sub-task อยู่แล้ว shell จึงเขียนนอกขอบไม่ได้ ซึ่งปิดช่องโหว่ที่เขามี
5. **ประเภทงาน → chain โมเดล + บัญชี AI**
   - เพิ่ม "ประเภทงาน" (เร็ว/ลึก/ดีไซน์/รีวิว) ในหน้าบัญชี AI โดยแต่ละประเภทเลือก chain โมเดลได้
   - failover ระหว่างบัญชีที่เรามีอยู่แล้วทำงานใต้ chain นั้นอีกชั้น
   - เก็บค่าใน config ของ HPK เอง ไม่เขียนทับ config ของ Hermes ทุกตาแบบเขา
6. **คิวการ steer ที่ซื่อสัตย์:** ข้อความที่พักไว้ให้มีป้าย "อ่านแล้ว / ไม่ได้ใช้" และส่ง steer เจาะจง sub-task ได้จากแถบ sub-task
7. **Approvals เร็วขึ้น**
   - เพิ่มปุ่ม 1/2/3, ตอบแล้วยุบการ์ด และกด J เพื่อไปคำขอถัดไป
   - **แยกคำสั่ง shell ที่ต่อกันออกเป็นแถวพร้อมระบุความเสี่ยง** แล้วจับคู่กับเส้นแดงของเรา
8. **ความรู้มีเหตุผลกำกับ:** "บันทึกลง wiki" ให้ผ่านขั้น *เก็บ / ปฏิเสธ / เลื่อน พร้อมเหตุผล* และปฏิเสธความลับกับ log อัตโนมัติ ส่วน recall ก่อนเริ่มแชทให้มีงบ token ที่เห็นได้
9. **ค่าใช้จ่ายไม่โกหก:** ถ้าไม่รู้ราคาให้แสดง "ไม่ทราบ" ไม่แสดง 0 และหยุดรีเฟรชเมื่อแท็บถูกซ่อน (ทำอยู่แล้วบางส่วน)

**สิ่งที่ไม่ควรเอาตามเขา:**

- skill 150 ตัวกับ prefix workflow 10 ตัวที่ผู้ใช้ต้องจำ ให้ agent เลือกเองหลังแชทเดียว
- sidebar ที่รวมทุกอย่าง
- การเขียนทับ config ของ Hermes ทุกตา
- โค้ดขนาดยักษ์
