## 1. ที่มา

ผู้ใช้ Hermes ที่ทำงานกับโปรเจคจริงเจอปัญหาเดียวกัน:

- **ความรู้หาย** — สิ่งที่ agent เรียนรู้อยู่ในแชทเก่า ถูกบีบอัดทิ้ง หรือยัดลง MEMORY.md จนเต็ม (2,200 ตัวอักษร)
- **กฎกับความรู้ปนกัน** — skill ของโปรเจคมีทั้งขั้นตอนและข้อเท็จจริงจนยาวและล้าสมัย
- **งานหลายสายคุมยาก** — สร้าง session ลูกได้แค่ทาง CLI, ไม่เห็นความสัมพันธ์แม่-ลูก, ชื่อ session ไม่เป็นระเบียบ, ตัวประสานงานต้องไล่ดู git เอง
- **คนหลุดออกจากกระบวนการ** — มีแค่ "ถามทุกคำสั่ง" กับ "YOLO" ไม่มีจุดตัดสินใจที่ออกแบบไว้

**Hermes Project Kit** คือชุดต่อเติม Hermes (ไม่แก้แกน) ที่ให้แต่ละโปรเจคมี **คลังความรู้ (wiki) ของตัวเอง**, **ระบบงานแม่-ลูก**, และ **คนอยู่ในกระบวนการ** โดยเร็วและประหยัด token

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย

**เป้าหมาย**
1. เพิ่มโปรเจคใหม่ได้ด้วยคำสั่งเดียว พร้อมวิเคราะห์และนำความรู้เข้า wiki (ถามก่อนเสมอ)
2. ความรู้สะสมอัตโนมัติ ตรวจย้อนได้ และไม่หายเมื่อบีบอัด context
3. งานแม่-ลูกที่มองเห็นได้ใน **HPK Console** (หน้าเว็บของเราเอง) พร้อมสรุปส่งกลับ
4. มีโหมด Manual / Ask / Auto พร้อม "เส้นแดง" ที่ไม่มีโหมดไหนข้ามได้
5. แยกข้อมูลของแต่ละโปรเจค และ **ปิดการแชร์ความรู้ลงส่วนกลางได้** สำหรับโปรเจคลับ
6. ติดตั้งได้บนทุก OS ที่ Hermes รองรับ ข้อมูลผู้ใช้อยู่ในเครื่องผู้ใช้เท่านั้น

**ไม่ใช่เป้าหมาย**
- ไม่ติดตั้ง Hermes ให้ (ผู้ใช้ต้องมีอยู่แล้ว)
- ไม่ fork / แก้โค้ดแกนของ Hermes Agent
- **ไม่ใช้ ไม่คัดลอก และไม่พึ่งโค้ดหรือ API ของ Hermes WebUI** (โปรเจคของบุคคลที่สาม) — กันปัญหาภายหลัง (§22)
- ไม่มี vector DB หรือบริการภายนอกในเวอร์ชันแรก
- ไม่สร้าง board งานใหม่ — ใช้ board ที่โปรเจคมีอยู่ (ไฟล์ markdown, Hermes Kanban หรือไม่มีก็ได้)

**ส่วนประกอบ**

| ส่วน | หน้าที่ | ทำไมเลือกแบบนี้ |
|---|---|---|
| `hpk` CLI | งาน deterministic ทั้งหมด + สร้าง/เปลี่ยนชื่อ session ผ่าน interface ทางการของ Hermes + ตัวรัน hook | P7, P8 — agent อ่านวิธีใช้จาก skill เมื่อจำเป็น ไม่เสีย token กับ tool schema ทุกรอบ |
| `hpk serve` (daemon) | เสิร์ฟ HPK Console, board API, แจ้งเตือน, งานตรวจที่ไม่ใช้ LLM, ACP client | ไม่ต้องปลุก Hermes agent มาทำงานที่ไม่ต้องคิด; hook ส่งเรื่องให้ daemon แทนแย่ง lock กันเอง |
| Skills | ขั้นตอนการทำงานให้ agent | progressive disclosure ของ Hermes อยู่แล้ว |
| Hooks | บังคับเส้นแดง, เก็บความรู้ก่อนบีบอัด, รายงานเมื่อลูกจบ | สิ่งที่ "ต้องเกิดเสมอ" ไม่ควรพึ่งความจำของโมเดล |
| Cron | งานเบื้องหลังรายวัน/สัปดาห์ | ใช้ scheduler ของ Hermes, รันด้วยโมเดลถูก/batch |
| HPK Console | หน้าเว็บของเราเอง: แผงควบคุม + แชทเบา (§22.4) | ไม่พึ่ง WebUI (P10); ฝังใน binary เดียว ไม่ต้องติดตั้งแยก |

## 5. การจัดเก็บข้อมูล

### 5.1 Process → Profile → Project (แก้ไข — ดู §25)
~~หนึ่งโปรเจค = หนึ่งโปรไฟล์~~ เปลี่ยนเป็นสามชั้น: Process (วิธีทำงาน) → Profile (= โปรไฟล์ของ Hermes) → Project
Profile เดียวใช้ได้หลายโปรเจค; wiki, board, audit และความเป็นส่วนตัวติดอยู่กับ **โปรเจค** ไม่ใช่โปรไฟล์

```
<HERMES_HOME>/
├── profiles/<profile>/              โปรไฟล์ของ Hermes (โมเดล, skills, memory, บุคลิก)
│   ├── memories/MEMORY.md           ตัวชี้ทางสั้นๆ เท่านั้น
│   └── hpk/profile.yaml             ค่าระดับ Profile + process ที่ใช้
├── hpk/
│   ├── processes/<process>.yaml     ค่าระดับ Process (ใช้ซ้ำได้)
│   └── projects/<project>/
│       ├── project.yaml             profile ที่ใช้, ประเภท (ส่วนตัว/ทีม), สมาชิก, ค่าแก้ทับ (§5.3)
│       ├── state.json               commit ล่าสุดที่วิเคราะห์, hash ไฟล์, งานค้าง
│       ├── board.db · audit.log
│       └── wiki/                    คลังความรู้ของโปรเจค (§7) — git repo ในตัว
└── hpk-shared/                      wiki ส่วนกลาง (§6): team/ และ users/<id>/
```
`WIKI_PATH` ไม่ตั้งตายตัวใน `.env` ของโปรไฟล์อีกต่อไป — hpk ส่งให้ตอนเริ่ม session ตามโปรเจคที่ทำงานอยู่

### 5.2 แบ่งหน้าที่ของที่เก็บ
| ที่เก็บ | เก็บอะไร | ใครเขียน |
|---|---|---|
| รีโปของโปรเจค (HANDOFF, BOARD, CLAUDE.md…) | **กฎ** และ **สถานะปัจจุบัน** | คน / agent ตามกฎโปรเจค |
| wiki ของโปรเจค | **ความรู้สะสม** (เหตุผล, สถาปัตยกรรม, บทเรียน, ประวัติ) | agent ผ่าน drafts + คนอนุมัติ |
| wiki ส่วนกลาง | บทเรียนทั่วไป, วิธีทำงานที่ผู้ใช้ชอบ | เฉพาะที่ "เลื่อนขึ้น" จากโปรเจคที่อนุญาต |
| MEMORY.md / USER.md | ตัวชี้ทาง ("wiki อยู่ที่ X อ่าน index.md ก่อน") | hpk |
| Skill ของโปรเจค | **ขั้นตอน** เท่านั้น | คน / agent (ไฟล์ควบคุม agent → ต้องอนุมัติ) |

กฎขัดกันเมื่อไร: **ผู้ใช้ในแชท > รีโปโปรเจค > wiki > skill** — wiki ห้ามมี "กฎ" ที่ไม่มีในรีโป

### 5.3 `project.yaml`
```yaml
name: my-app
root: ~/code/my-app
language: th                     # ภาษาที่ใช้คุยกับผู้ใช้
privacy:
  mode: shared                   # shared | private | isolated  (§6)
  model_policy: any              # any | local_only
board:
  kind: markdown                 # hpk | markdown | hermes-kanban | none  (§20.2)
  file: BOARD.md
  stale_after_minutes: 30        # claim ไม่มี heartbeat เกินนี้ → stale (§20.3)
  lane_notes: notes/sessions/{lane}.md
worktrees:
  dir: worktrees/
session:
  title_template: "Version {version} {name}"
  ask_on_start: [version]        # ข้อมูลที่ต้องถามตอนเริ่มงาน
gates:
  default_mode: ask              # manual | ask | auto
  red_lines_extra:               # เพิ่มจากชุดค่าเริ่มต้น §11.2
    - "รัน make release-check ก่อน merge"
checks:
  test: "make test"
ingest:
  include: ["README.md", "docs/**", "notes/**", "*.md"]
  exclude: ["**/.env*", "**/secrets/**", "node_modules/**"]
budget:
  ingest_max_tokens: 400000
  nightly_max_tokens: 60000
delivery: console                # console | telegram | line | … (ช่องทางอื่นผ่าน gateway ของ Hermes)
```

## 6. ความเป็นส่วนตัว และ wiki ส่วนกลาง

### 6.1 สามระดับ (ตั้งต่อโปรเจคใน `privacy.mode`)
| โหมด | เขียนลงส่วนกลาง | อ่านจากส่วนกลาง | ใช้เมื่อ |
|---|---|---|---|
| **shared** (ค่าเริ่มต้น) | ได้ — ผ่านการ "เลื่อนขึ้น" ที่คนอนุมัติ | ได้ | โปรเจคทั่วไป |
| **private** | **ไม่ได้เลย** | ได้ | โปรเจคลับที่ยังอยากได้บทเรียนทั่วไป |
| **isolated** | ไม่ได้ | **ไม่ได้** | โปรเจคลับมาก ไม่ให้มีอะไรข้ามมาเลยทั้งสองทาง |

### 6.2 การ "เลื่อนขึ้น" ส่วนกลาง (เฉพาะโปรเจค shared)
1. lint รายสัปดาห์เสนอหน้าที่ดูเป็นความรู้ทั่วไป (เช่น บทเรียนเรื่อง git, วิธีทำงานที่ผู้ใช้ชอบ)
2. hpk สร้างร่าง **ที่ตัดชื่อโปรเจค ลูกค้า path URL และข้อมูลเฉพาะออก** แล้ว
3. คนอนุมัติทีละข้อ — ไม่มีโหมด Auto สำหรับการเลื่อนขึ้น (เป็นเส้นแดง)
4. หน้าที่เลื่อนขึ้นจำที่มาแบบไม่เปิดเผย (`origin: project-hash`) เพื่อย้อน/ลบได้

### 6.3 การป้องกันในโปรเจค private / isolated
- hook ปฏิเสธการเขียนไปที่ `hpk-shared/` จากโปรไฟล์นี้ (ไม่ใช่แค่ "ไม่เสนอ")
- สรุปและรายการร่างส่ง **เฉพาะช่องทางในเครื่อง (HPK Console)** — ห้ามส่งไป Telegram/LINE/อีเมล
- ไม่รวมข้อมูลโปรเจคนี้ในสรุปข้ามโปรเจคใดๆ
- `model_policy: local_only` (ตัวเลือก) — งาน ingest/lint ใช้เฉพาะโมเดลในเครื่อง (Ollama / LM Studio); ถ้าไม่มีโมเดลในเครื่อง งานจะหยุดแล้วถาม ไม่สลับไปใช้ cloud เอง
- เปลี่ยนโหมดจาก private → shared ต้องยืนยันโดยคน และ **ไม่** ย้อนเลื่อนความรู้เก่าขึ้นส่วนกลางอัตโนมัติ

## 7. Wiki

### 7.1 โครงสร้าง (ต่อโปรเจค)
```
wiki/
├── SCHEMA.md       กติกา wiki ของโปรเจคนี้ (สร้างจาก template)
├── index.md        สารบัญ หนึ่งบรรทัดต่อหน้า (≤ ~2k token)
├── log.md          บันทึกตามเวลา append-only
├── raw/            ต้นฉบับห้ามแก้: สรุป session, git log, สกัดจากเอกสาร
├── decisions/      การตัดสินใจ + เหตุผล + ทางเลือกที่ไม่เลือก
├── architecture/   ส่วนประกอบระบบและการเชื่อมกัน
├── versions/       ประวัติแต่ละเวอร์ชัน/lane
├── lessons/        บทเรียน/ปัญหาที่เจอ + วิธีแก้
├── glossary/       คำศัพท์, ลูกค้า, หน่วยงาน
├── people/         ใครดูแลอะไร, วิธีทำงานที่ชอบ
└── _drafts/        ร่างรออนุมัติ (+ stale/)
```

### 7.2 กติกาของหน้า
- ทุกหน้ามี front-matter: `title, type, sources[], updated, confidence`
- **ทุกข้ออ้างต้องมีที่มา** (ไฟล์+บรรทัด, commit, session id) — ไม่มีที่มา = ไม่รับ
- หน้าละ ≤ ~1.5k token; ยาวกว่านั้นให้แยก
- ห้ามเขียนกฎลง wiki — ถ้าเจอกฎ ให้เสนอแก้ในรีโปแทน

### 7.3 สิทธิ์การเขียน
| ส่วน | Ask (ค่าเริ่มต้น) | Auto |
|---|---|---|
| `log.md`, `raw/` | เขียนเองได้ | เขียนเองได้ |
| `lessons/`, `versions/`, `glossary/` | ผ่านร่าง → คนอนุมัติ | อนุมัติเอง + บันทึก audit |
| `decisions/`, `architecture/`, `people/` | ผ่านร่าง → คนอนุมัติ | **ผ่านร่าง → คนอนุมัติ** |
| `SCHEMA.md` | คนเท่านั้น | คนเท่านั้น |

### 7.4 ขั้นตอนอนุมัติร่าง
1. agent เขียนร่างที่ `_drafts/<n>-<slug>.md` พร้อมหัวสรุป: เพิ่ม/แก้อะไร, ที่มา, หน้าที่กระทบ
2. ส่งรายการเป็นข้อมีเลขผ่านช่องทาง `delivery` หรือหน้าอนุมัติใน HPK Console
3. ผู้ใช้ตอบ "อนุมัติ 1,3 / แก้ 2 ว่า… / ทิ้ง 4"
4. hpk ย้ายเข้าที่จริง → อัปเดต `index.md` → `log.md` → `git commit`
5. ร่างค้างเกิน 14 วัน → `_drafts/stale/` (ไม่ลบ)

### 7.5 การค้นคืน
ลำดับ: `index.md` → ripgrep ใน wiki → ค้นข้อความใน `state.db` (session เก่า) — ไม่มี embedding ในเวอร์ชันแรก

## 9. ระบบงานแม่-ลูก

- **สร้างลูก:** `hpk session new --parent <sid> --title … --worktree … --brief <file>` → hpk เปิด session ใหม่ผ่าน **ACP** (`hermes-acp`) หรือ `hermes chat` → บันทึกความสัมพันธ์แม่-ลูกใน `board.db` ของเราเอง (ไม่พึ่งว่า UI ไหนจะแสดงแท็บอะไร)
- **ข้อดีของ ACP:** hpk เป็น client ของ session ที่มันสร้าง → คำขออนุญาต (permission request) ของ session นั้นมาที่ hpk → แสดงเป็นกล่องอนุมัติใน Console ได้ (ดู §11.2, §18 ข้อ 2)
- **auth:** ไม่ต้องล็อกอิน UI ของใคร — ACP/CLI รันในเครื่องเดียวกับ Hermes; dashboard API ทางการใช้เฉพาะเมื่อจำเป็น ด้วย session token ที่ผู้ใช้ตั้งเอง
- **brief มาตรฐาน:** งานคืออะไร, ไฟล์/หน้า wiki ที่ต้องอ่าน, เส้นแดงของโปรเจค, รูปแบบสรุปที่ต้องส่งกลับ
- **สรุปส่งกลับ (hook เมื่อลูกจบรอบ):** รูปแบบตายตัว ≤ 15 บรรทัด — ทำอะไร / ตัดสินใจอะไร / บทเรียน / ค้างอะไร / คำถามถึงคน → ส่งเข้าแชทแม่ + `wiki/raw/` + `log.md`
- **คำถามจากลูก:** ส่งขึ้นแม่ก่อน; แม่ตอบไม่ได้ → ถึงคน (ทุกโหมด)
- **HPK Console:** ต้นไม้แม่-ลูก + ป้ายสถานะ (ทำอยู่ / รอคน / เสร็จ / ล้ม), ปุ่มหยุด/รีสตาร์ทลูก, หน้า Lanes (lane → session → branch → git status → commit ล่าสุด)
- **ข้อจำกัดโดยตั้งใจ:** จำนวนลูกพร้อมกันมีเพดาน (ค่าเริ่มต้น 4) และแต่ละลูกทำงานใน worktree ของตัวเอง

## 10. ตั้งชื่อ session อัตโนมัติ

- รูปแบบจาก `session.title_template`; ค่าที่ไม่รู้ (เช่น version) ถามตอนเริ่มงานตาม `ask_on_start`
- เปลี่ยนชื่อผ่าน `hermes sessions rename` (CLI ทางการ) → Console อัปเดตทันทีผ่าน SSE ของ hpk เอง
- ชื่อที่ตรง template ถือเป็น "ชื่อที่ตั้งแล้ว" — งานตั้งชื่ออัตโนมัติของ hpk จะไม่ทับ (UI อื่นที่ผู้ใช้อาจเปิดอยู่ ไม่อยู่ในความรับผิดชอบของเรา)
- ลูกได้ชื่อจากแม่ + ชื่องาน เช่น `Version 1.4.0 auth › api-tests`

## 11. คนในกระบวนการ

### 11.1 โหมด
| โหมด | agent ทำเอง | ต้องถาม |
|---|---|---|
| Manual | อ่าน, ร่าง, เขียน log | การเขียน/รันคำสั่งทุกอย่าง |
| **Ask (ค่าเริ่มต้น)** | อ่าน, แก้ใน worktree ของ lane, commit ในเครื่อง, เขียน log/raw | จุดตัดสินใจ §11.3 |
| Auto | ใช้ approvals `smart` ของ Hermes ตัดสินเอง | เส้นแดงเท่านั้น |

- เปิด Auto ได้ระดับ session / lane / มีเวลาหมด (`/auto 2h`) / ค่าตั้งโปรไฟล์
- ป้ายโหมดแสดงในช่องพิมพ์ตลอด; `/auto off` หรือ Stop กลับเป็น Ask ทันที

### 11.2 เส้นแดง (ถามคนทุกโหมด)
ชุดค่าเริ่มต้น + `gates.red_lines_extra` ของโปรเจค:
1. push / tag / เปิด MR-PR / merge เข้า branch หลัก
2. ลบทุกอย่าง (ไฟล์, โฟลเดอร์, worktree, branch, DB, หน้า wiki)
3. อ่านหรือแสดงค่าใน `.env` / ไฟล์ลับ
4. แก้ไฟล์ที่ควบคุม agent (AGENTS.md, CLAUDE.md, SOUL.md, skills, `project.yaml`, `SCHEMA.md`)
5. เปลี่ยนโมเดลกลางแชท / ใช้ token เกินงบ
6. แก้ `decisions/` `architecture/` `people/` ใน wiki
7. เลื่อนความรู้ขึ้นส่วนกลาง / เปลี่ยนโหมดความเป็นส่วนตัว
8. ส่งข้อมูลออกนอกเครื่อง (ข้อความถึงคนอื่น, แพลตฟอร์มแชท) ที่ไม่ใช่ช่องทาง `delivery` ที่ตั้งไว้

**กลไก:** Hermes มี `approvals.deny` (ห้ามเด็ดขาด ข้าม YOLO ไม่ได้) และ protected instruction files (ถามเสมอ) แต่ยังไม่มี "ถามเสมอ" สำหรับคำสั่งทั่วไป → ต้องทำ hook `red-line guard` (ดู §18 ข้อ 2)

### 11.3 จุดตัดสินใจ (โหมด Ask)

| 2 | แผนงานใหญ่ | ไปต่อได้ถ้าอยู่ในขอบเขตที่ตกลง (ต้องโพสต์แผน) |
| 3 | แจก lane / สร้างลูก | สร้างเอง + รายงานตาราง |

| 5 | merge / push | เส้นแดง |
| 6 | ร่าง wiki | ตาม §7.3 |
| 7 | ลบ | เส้นแดง |
| 8 | ทบทวนรายสัปดาห์ | สำคัญขึ้น — ตรวจย้อนงานของ Auto |

### 11.4 ตรวจย้อนได้
- ทุกการตัดสินใจ (คนหรือ Auto) ลง `hpk/audit.log` และ `wiki/log.md`:
  `[auto] 2026-11-16 14:32 อนุมัติ lessons/session-lock.md — เพิ่มเติม ไม่ขัดของเดิม`

### 11.5 พูดแบบเพื่อนร่วมทีม

## 12. งานตั้งเวลา (cron)

| งาน | เวลา (ปรับได้) | ทำอะไร | โมเดล |
|---|---|---|---|
| nightly ingest | ทุกคืน 02:00 | session + git log ของวันนั้น → `raw/` + `log.md` → ร่างหน้าหลัก | ถูก / batch |
| weekly lint | จันทร์ 08:00 | หาข้อขัดแย้ง, หน้าเก่า, หน้าไม่มีลิงก์ถึง, เสนอเลื่อนขึ้นส่วนกลาง → รายงาน | หลัก |
| auto digest | ทุกวัน 18:00 (เฉพาะวันที่เปิด Auto) | สรุปการตัดสินใจของ Auto | ถูก |

ทุกงาน: มี lock กันรันซ้อน, ทำซ้ำได้ไม่พัง, ทำต่อจากจุดค้างได้, มีเพดาน token และบันทึกค่าใช้จ่ายลง `log.md`

## 13. ความเร็วและการประหยัด token

| # | วิธี | ผล |
|---|---|---|
| 1 | สคริปต์ก่อน LLM (scan, git, index, diff) | งานสำรวจ = 0 token |
| 2 | แยกระดับโมเดล (Auxiliary Models ของ Hermes) | งานเล็กใช้โมเดลถูก |
| 3 | งานกลางคืนใช้ batch API | ถูกลงราวครึ่งหนึ่ง (ตามราคาผู้ให้บริการ) |

## 14. ความปลอดภัย
- ไม่อ่าน `.env` / ไฟล์ลับ; สแกนและ redact สิ่งที่หน้าตาเหมือน key ก่อนส่งให้ LLM
- token/รหัสผ่านทั้งหมด (Console, dashboard ทางการ) มาจาก env เท่านั้น ไม่เขียนลงไฟล์
- ข้อมูลผู้ใช้ทั้งหมดอยู่ใน `<HERMES_HOME>` ไม่เคยอยู่ในรีโปของ Project Kit
- HPK Console ผูกกับ 127.0.0.1 เป็นค่าเริ่มต้น; เปิดออกเครือข่ายได้เฉพาะเมื่อตั้ง auth (รหัสผ่าน/passkey/OIDC) และ TLS แล้ว
- hpk อ่าน `state.db` ของ Hermes แบบ **อ่านอย่างเดียว** — ไม่เขียนข้อมูลของ Hermes ตรงๆ (เขียนผ่าน CLI/ACP เท่านั้น)
- เส้นแดง §11.2 และการป้องกันโปรเจคลับ §6.3 บังคับด้วย hook ไม่ใช่แค่คำสั่งใน prompt

## 15. การติดตั้ง แจกจ่าย และเวอร์ชัน
- แจกเป็น git repo เดียว; `hpk install` ติดตั้ง skills, hooks และ cron templates ลงโปรไฟล์ที่เลือก (วิธีที่ Hermes รองรับจริงต้องตรวจ — §18 ข้อ 1); Console มากับ binary ไม่ต้องติดตั้งแยก
- `hpk doctor`: ตรวจเวอร์ชัน Hermes, `hermes`/`hermes-acp` ใช้ได้, `WIKI_PATH`, hooks, cron, auth ของ Console
- `hpk uninstall`: ถอดส่วนต่อเติม **ไม่แตะ wiki ของผู้ใช้** (ลบ wiki ต้องสั่งแยกและยืนยัน)
- เวอร์ชันแบบ SemVer; ระบุช่วงเวอร์ชัน Hermes ที่รองรับ; ชุดทดสอบ `hpk selftest` รันหลังอัปเดต Hermes
- แจก **binary ไฟล์เดียว** ต่อ OS/สถาปัตยกรรม (§21) — ไม่ต้องมี Python/Node และไม่ผูกกับ venv ของ Hermes; ไม่มี path ผูก OS

## 18. คำถามค้าง / ต้องตรวจสอบ (M0) — **ตอบแล้ว ดู [`m0-findings.md`](m0-findings.md)**
1. Hermes ติดตั้ง skill/hook/cron จาก git repo ได้แบบไหน (Skills hub? copy ไฟล์?)
2. hook ของ Hermes บังคับ "ถามคน" ก่อนรันคำสั่งได้ไหม หรือได้แค่ allow/deny — **ทางเลือกใหม่:** session ที่ hpk สร้างผ่าน ACP จะส่ง permission request มาที่ hpk → ถามคนใน Console ได้เอง (ต้องยืนยันว่า Hermes ส่งคำขอทุกคำสั่งที่ต้องอนุมัติผ่าน ACP)
3. มี hook "ก่อนบีบอัด context" และ "เมื่อ session จบรอบ" ให้ใช้หรือไม่ (เอกสารกล่าวถึง pre-compress checkpoint ของ memory provider)
4. `hermes-acp` รองรับอะไรบ้าง: สร้าง/โหลด session, ตั้งชื่อ, cwd/worktree, โปรไฟล์, permission request, ยกเลิก — และเก็บความสัมพันธ์แม่-ลูกฝั่ง Hermes ได้ไหม (ถ้าไม่ได้ เก็บใน `board.db` ของเรา)
5. `WIKI_PATH` ใน `.env` ของโปรไฟล์ ถูก skill `llm-wiki` ของ Hermes อ่านตามโปรไฟล์ที่ active หรือไม่
6. cron ของ Hermes เลือกโมเดล batch และตั้งเพดาน token ต่องานได้ไหม
7. ชื่อโปรเจคจริง (ตอนนี้ใช้ "Hermes Project Kit" / `hpk` เป็นชื่อชั่วคราว)
8. บน server หลายคน: Hermes แยก session ตามผู้ใช้ได้ไหม (Console เป็นคนรู้ตัวตน แล้วติดป้ายเจ้าของให้ session เอง) (§19)
9. ส่งข้อความเข้า session ที่กำลังทำงานแบบ "ต่อคิว" (ไม่ขัดจังหวะ) ผ่าน ACP หรือ `hermes` CLI ได้ไหม (§20.5)
10. ใช้ claim ของ Hermes Kanban (`claim_lock`, `claim_expires`) เป็น backend ของ board ได้ไหม ถ้าโปรเจคยอมใช้ Kanban (§20.2)
11. รูปแบบ input/output ของ hook Hermes (stdin JSON? exit code? ข้อความกลับ) เพื่อให้ `hpk hook <name>` ทำตามได้ตรง
12. Hermes ให้ binary ภายนอกเรียก `hermes` CLI ได้ครบ (chat -q, sessions, cron) บนทุก OS ไหม — เป็นทางที่ hpk ใช้สั่งงาน LLM

## 19. ทำงานเป็นทีมบน Server

### 19.1 รูปแบบการติดตั้ง
| รูปแบบ | ใช้เมื่อ | หมายเหตุ |
|---|---|---|
| **Solo** (ค่าเริ่มต้น) | คนเดียว เครื่องเดียว | ทุกอย่างตามที่ออกแบบด้านบน |
| **Team server** | ทีมใช้ Hermes ตัวเดียวบน server | Hermes Agent + `hpk serve` (Console) ใน Docker/systemd + reverse proxy + TLS — ไม่ต้องมี Hermes WebUI |

`project.yaml` เพิ่ม:
```yaml
team:
  enabled: true
  members:                       # ตัวตนมาจาก OIDC / trusted header ไม่ใช่ตั้งเอง
    - { id: "alice@corp", role: owner }
    - { id: "bob@corp",   role: member }
  approvers:                     # ใครอนุมัติอะไรได้
    wiki_core: [owner, maintainer]      # decisions/ architecture/ people/
    red_lines: [owner, maintainer]
    promote_shared: [owner]
  notify: console                # console | email | slack | … (ช่องทางอื่นผ่าน gateway ของ Hermes)
```

### 19.2 ตัวตนและบทบาท
- HPK Console ทำ auth เอง (เขียนใหม่ทั้งหมด ไม่ใช้โค้ด WebUI): **OIDC** (Keycloak, Authentik, Google…), **passkey**, หรือ **trusted header** จาก reverse proxy (เช่น Authelia/oauth2-proxy)
- ผูกกลุ่มกับโปรเจคใน config ของ hpk เช่น `team-alpha → my-app` → ทีมเห็นเฉพาะโปรเจคของตัวเอง
- บทบาท: **owner** (ตั้งค่า, อนุมัติทุกอย่าง) · **maintainer** (อนุมัติ wiki หลัก + เส้นแดง) · **member** (ทำงาน, อนุมัติร่างทั่วไป) · **viewer** (อ่านอย่างเดียว)
- ทุกการกระทำใน `audit.log` / `log.md` ระบุ **ใคร** (คน หรือ session ของใคร)

### 19.3 ข้อมูลในโหมดทีม
| ข้อมูล | ขอบเขต |
|---|---|
| wiki ของโปรเจค | ของทีม (ทุกคนในโปรเจคอ่านได้, เขียนตามสิทธิ์ §7.3 + บทบาท) |
| `people/` | ของทีม — แต่ละคนแก้หน้าของตัวเองได้, หน้าคนอื่นต้องผ่านร่าง |
| USER.md / วิธีทำงานที่ชอบ | **ส่วนตัวต่อคน** — ไม่แชร์ในทีม |
| wiki ส่วนกลาง | แยกเป็น **ส่วนกลางของทีม** (`hpk-shared/team/`) และ **ส่วนกลางส่วนตัว** (`hpk-shared/users/<id>/`) |
| session | ของเจ้าของ — คนอื่นเห็นชื่อ/สถานะบน board แต่เปิดอ่านแชทได้เฉพาะเมื่อเจ้าของแชร์ |
| งบ token | ต่อโปรเจค + ต่อคน (เกินแล้วหยุดถาม) |

โหมดความเป็นส่วนตัว §6 ใช้เหมือนเดิม: โปรเจค `private`/`isolated` ไม่เขียนลงส่วนกลางของทีมด้วย

### 19.4 ทำงานพร้อมกันหลายคน
- wiki เป็น git: hpk ใช้ **lock ต่อหน้า** ตอนอนุมัติ/ย้ายร่าง + commit ทีละรายการ → ไม่มี merge conflict
- ร่างที่แก้หน้าเดียวกันสองชิ้น → hpk รวมเป็นรายการเดียวให้ผู้อนุมัติเลือก
- cron ของโปรเจครันครั้งเดียวต่อโปรเจค (ไม่ใช่ต่อคน) และสรุปส่งถึงผู้อนุมัติตามบทบาท
- การกันงานซ้ำระหว่างคน/ระหว่าง session → §20

### 19.5 ความปลอดภัยบน server
- บังคับ auth (ห้ามรันแบบ Unauthenticated), TLS, `HERMES_WEBUI_ALLOWED_ORIGINS`
- เส้นแดงอนุมัติได้เฉพาะบทบาทใน `approvers.red_lines` — คนที่สั่งงานอาจไม่มีสิทธิ์อนุมัติเอง
- สำรอง `<HERMES_HOME>` (wiki + board + audit) ทุกคืน; hpk มี `hpk backup` / `hpk restore`
- secret ของโปรเจคอยู่ใน env ของ server เท่านั้น ไม่อยู่ใน wiki / board

## 20. BOARD และการกันงานซ้ำ (claims + แจ้งเตือน)

### 20.1 ปัญหา
หลาย session (ของคนเดียวกันหรือคนละคน) อาจเริ่มงานเดียวกัน หรือแก้ไฟล์ชุดเดียวกันโดยไม่รู้ตัว — ต้องรู้ **ก่อน** เริ่ม และรู้ **ระหว่าง** ทำ

### 20.2 HPK Board
board ของ hpk มีสองชั้น:
- **ข้อมูลจริง:** `hpk/board.db` (SQLite, ต่อโปรเจค) — งาน, claim, heartbeat, ข้อความ — เขียนพร้อมกันได้ปลอดภัย
- **มุมมองสำหรับคน:** `BOARD.md` สร้างจาก board.db อัตโนมัติ (ตาราง lane/งาน/ใครทำ/สถานะ) — คนยังเปิดอ่านได้เหมือนเดิม

ตัวเลือก `board.kind` ใน `project.yaml`:
| kind | ข้อมูลจริงอยู่ที่ | ใช้เมื่อ |
|---|---|---|
| `hpk` (แนะนำ) | `board.db` → render `BOARD.md` | โปรเจคใหม่ / ทีม |
| `markdown` | `BOARD.md` ที่คนแก้เอง + claims แยกใน `board.db` | โปรเจคเดิมที่มี BOARD.md อยู่แล้ว — hpk แก้เฉพาะส่วนที่มี marker `<!-- hpk:claims -->` |
| `hermes-kanban` | Kanban ของ Hermes (มี claim/expiry ในตัว) | โปรเจคที่ยอมใช้ Kanban (ต้องตรวจ §18 ข้อ 10) |

### 20.3 Claim — "ฉันกำลังทำสิ่งนี้"
```yaml
claim:
  id: c-0142
  task: "auth: เพิ่ม refresh token"     # หรือ lane
  scope:
    lane: auth
    paths: ["web/src/auth/**", "workspace-api/src/session/**"]
    wiki: ["decisions/auth-flow.md"]
  owner: { user: "alice@corp", session: "sid-9f2…" }
  started: 2026-11-16T14:02
  heartbeat: 2026-11-16T14:31            # อัปเดตทุก turn ผ่าน hook
  status: active                         # active | waiting-human | done | stale
```
- **เริ่มงาน:** hook ก่อน turn แรกของงาน → `hpk board check` หา claim ที่ทับ → ถ้าไม่ทับ `hpk board claim`
- **ระหว่างทำ:** hook ทุก turn อัปเดต heartbeat; เมื่อแตะไฟล์นอก `scope.paths` → ขยาย scope (และตรวจทับใหม่)
- **จบ:** `hpk board release` + สรุปลง wiki (§9)
- **ค้าง:** ไม่มี heartbeat เกิน 30 นาที → `stale` (ไม่ปลดเอง)

### 20.4 การตรวจว่าทับกัน (0 token — สคริปต์ล้วน)
| ระดับ | เงื่อนไข | สิ่งที่เกิด |
|---|---|---|
| 🔴 **ซ้ำ** | งาน/lane เดียวกัน | **หยุด** → แจ้ง + ให้เลือก (§20.6) |
| 🟠 **ทับไฟล์** | `paths` ซ้อนกัน หรือ worktree สองอันแก้ไฟล์เดียวกัน (`git diff --name-only`) | เตือน + เสนอประสานงาน ทำต่อได้ถ้าคนยืนยัน |
| 🟡 **เกี่ยวข้อง** | แตะหน้า wiki เดียวกัน / งานที่เป็น dependency | แจ้งให้รู้ ไม่หยุด |

นอกจากตอนเริ่มงาน ยังตรวจ **ทุก commit ในเครื่อง** (hook) และ **ทุกคืน** (cron ตี 2 เทียบทุก worktree)

### 20.5 ถาม session อื่น
- `hpk board who <งาน|path>` → ตอบจาก board ทันที (ใคร, session ไหน, heartbeat ล่าสุด) **ไม่ต้องรบกวน session นั้น**
- ถ้าข้อมูลบน board ไม่พอ (เช่น `stale`, หรืออยากรู้ความคืบหน้า): `hpk session ask <sid> "ยังทำ X อยู่ไหม / ถึงไหนแล้ว"`
  - ข้อความเข้า session ปลายทางแบบ **ต่อคิว** (ไม่ขัดจังหวะงาน) ด้วยรูปแบบตายตัว
  - session ปลายทางตอบสั้นตามรูปแบบ: สถานะ / ทำถึงไหน / คาดว่าเสร็จเมื่อไร / ไฟล์ที่กำลังแตะ
  - คำตอบกลับมาที่ผู้ถาม + อัปเดต claim
  - ไม่ตอบใน 10 นาที → ถือว่าไม่ว่าง → แจ้งเจ้าของ (คน)
- ข้าม session ของคนอื่นในทีม: ถามได้เฉพาะ "สถานะ" (ไม่เห็นเนื้อหาแชท) และเจ้าของได้รับแจ้งว่ามีคนถาม

### 20.6 เมื่อเจอ "ซ้ำ" — คนเป็นผู้ตัดสิน
แจ้งในแชทของ session ที่จะเริ่ม (และป้ายบนต้นไม้แม่-ลูกใน HPK Console):

> ⚠️ งาน **auth: refresh token** มีคนทำอยู่แล้ว — session `Version 1.4.0 auth` ของ alice (ล่าสุด 4 นาทีที่แล้ว)
> 1. รอจนเสร็จ (แจ้งเมื่อ release)
> 2. ทำส่วนอื่นแทน (เสนอส่วนที่ยังว่างจาก board)
> 3. ช่วยกัน — ส่งข้อความหา session นั้นเพื่อแบ่งงาน
> 4. ขอรับงานต่อ (ต้องให้เจ้าของ claim หรือ owner/maintainer อนุมัติ)

- โหมด Auto: เลือก 1 หรือ 2 เองได้, **3 และ 4 ต้องถามคนเสมอ** (เป็นเส้นแดง)
- งาน `stale`: แสดงตัวเลือกเดียวกัน + "ถาม session นั้นก่อน" (§20.5)

### 20.7 แจ้งเตือน
| เหตุการณ์ | ใครได้รับ | ที่ไหน |
|---|---|---|
| ซ้ำ / ทับไฟล์ ตอนเริ่ม | session ที่จะเริ่ม + เจ้าของ | แชท + ป้ายบน Console |
| ทับไฟล์ที่พบตอน commit / ตอนกลางคืน | เจ้าของทั้งสองฝั่ง | แชท + สรุปเช้า |
| claim กลายเป็น `stale` | เจ้าของ claim | ช่องทาง `notify` ของเขา |
| มีคนถามสถานะงานของเรา | เจ้าของ session | แชท (ไม่ขัดจังหวะ) |
| งานที่รออยู่ถูก release | คนที่เลือก "รอ" | แชท + `notify` |
| ลูกต้องการคน (`waiting-human`) | แม่ + เจ้าของ | ป้ายแดงบนต้นไม้ + `notify` |

กติกาแจ้งเตือน: รวมเป็นชุด (ไม่เกิน 1 ครั้ง/5 นาที/คน ยกเว้น 🔴), โปรเจค private ส่งเฉพาะช่องทางในเครื่อง/ในองค์กร

### 20.8 ต้นทุน
การตรวจทั้งหมดเป็นสคริปต์ + SQLite → **0 token**; LLM ใช้เฉพาะตอนตอบคำถาม `session ask` (โมเดลถูก, คำตอบรูปแบบตายตัว)

## 21. Tech Stack

### 21.1 เป้าหมายของ stack
ดี · **เร็ว** · **ปัญหาน้อย** · **ประหยัดตอนลง server** · ไม่ผูกกับ runtime ของ Hermes (Hermes อัปเดตแล้วของเราไม่พังตาม)

### 21.2 ที่มาของการตัดสินใจ (วัดจริงบนเครื่องพัฒนา, Windows 11)
| | เวลาเริ่มทำงานต่อครั้ง |
|---|---|
| Python ของ Hermes 3.14 (import sqlite3, json, urllib, yaml) | 230–290 ms |
| โปรแกรม native (git, รวม overhead ของ shell) | ~57 ms |

hook ของเรารันทุกครั้งที่ agent เรียกเครื่องมือ → Python เพิ่ม ~0.25 s/ครั้ง (งาน 200 tool calls ≈ +1 นาที) — และเครื่องผู้ใช้ Windows อาจไม่มี Python ของระบบเลย (เครื่องนี้ก็ไม่มี)

### 21.4 Hook ทำงานเร็วอย่างไร
- Hermes เรียก `hpk hook <name>` (binary เดียว เริ่มเร็ว)
- ถ้า `hpk serve` รันอยู่ → ส่งเรื่องทาง loopback (เร็ว, ไม่แย่ง lock SQLite)
- ถ้าไม่รัน → ทำเองกับ SQLite โดยตรง (ยังทำงานได้แม้ไม่มี daemon)
- เส้นแดงตั้ง `fail_closed: true` — hook พังเมื่อไร ปฏิเสธไว้ก่อน

## 22. อิสระจาก Hermes WebUI

### 22.1 กติกา
- **ไม่ใช้ ไม่คัดลอก ไม่ดัดแปลง** โค้ดของ Hermes WebUI (รวม `mcp_server.py`, ระบบ extension, รูปแบบ API ภายใน)
- **ไม่เรียก API ของ WebUI** และไม่อ่านไฟล์ข้อมูลของ WebUI (`webui/sessions/*.json`, `_index.json` ฯลฯ)
- ผู้ใช้ยังใช้ WebUI ควบคู่ได้ตามใจ — แต่ระบบของเรา **ไม่รู้และไม่สนใจ** ว่ามี WebUI อยู่หรือไม่
- ถ้าแนวคิดใดตรงกับ WebUI (เช่น ต้นไม้ session, กล่องอนุมัติ) ให้ออกแบบและเขียนใหม่จากสเปคของเราเอง

### 22.2 Interface ที่ใช้ได้ (ของ Hermes Agent, Nous Research, MIT)
| Interface | ใช้ทำอะไร | ความเสถียร |
|---|---|---|
| `hermes` CLI | chat -q, sessions list/rename/export, cron, profiles, approvals | สูง (เป็นหน้าบ้านหลัก) |
| **ACP** (`hermes-acp`, Agent Client Protocol) | สร้าง/คุย session, รับ permission request, ยกเลิก | สูง (มาตรฐานเปิด) |
| Hooks (`config.yaml`) | เรียก `hpk hook …` | สูง |

| `state.db` (อ่านอย่างเดียว) | ค้น session เก่า, ต้นไม้ delegation, สถิติ | กลาง — โครงสร้างอาจเปลี่ยน → ห่อด้วย adapter + ทดสอบใน CI |

## 24. บัญชี AI และการสลับบัญชีอัตโนมัติ (failover)

### 24.1 ความต้องการ
- ใส่ได้หลายบัญชีต่อหนึ่งค่าย (เช่น Anthropic: บริษัท / ส่วนตัว / Team pool)
- จัดลำดับการใช้เองได้ เมื่อบัญชีหนึ่ง token หรือโควตาหมด ให้สลับไปบัญชีถัดไปตามลำดับ

### 24.2 ที่เก็บและความปลอดภัย
- บัญชีเก็บใน **credential pool ของ Hermes** (`hermes auth …`, dashboard `/api/credentials/pool`) — hpk แค่จัดลำดับและสั่งสลับ
- Console แสดงแค่รหัสย่อ (fingerprint) ไม่แสดง key; key ที่กรอกส่งตรงไป Hermes แล้วล้างออกจากหน้าเว็บทันที
- เชื่อมต่อได้ 3 แบบ: API key · ล็อกอินกับผู้ให้บริการ (OAuth) · เลือกบัญชีที่ Hermes รู้จักอยู่แล้ว

### 24.3 กติกาการสลับ (ตั้งได้)

|---|---|

## 25. Process → Profile → Project และโปรเจคส่วนตัว/ทีม

### 25.1 สามชั้น
| ชั้น | คืออะไร | ตัวอย่างค่า | ใช้ซ้ำ |
|---|---|---|---|
| **Process** | วิธีทำงาน | โหมดเริ่มต้น, Auto นานสุด, จุดตัดสินใจ, เส้นแดงเพิ่ม, ชนิด board, งานตั้งเวลา, รูปแบบชื่อ session, ร่าง wiki ที่ต้องตรวจ, session ลูกสูงสุด, งบต่อวัน | หลาย Profile |
| **Profile** | ตัวตนของ agent (= โปรไฟล์ Hermes) | โมเดลหลัก/โมเดลวางแผน, บัญชี AI ตามลำดับ (§24), skills, บุคลิก, ชุดเครื่องมือ, ภาษา | หลายโปรเจค |
| **Project** | สิ่งที่ทำงานด้วย | รีโป, wiki, board, ความเป็นส่วนตัว, ประเภท (ส่วนตัว/ทีม), สมาชิก, ค่าแก้ทับ | — |

### 25.2 กติกาการสืบทอด
- ค่าที่ใช้จริง = **Project ?? Profile ?? Process ?? ค่าในตัว** (ชั้นล่างชนะ)
- แต่ละค่ากำหนดได้ว่าแก้ที่ชั้นไหนได้ (เช่น `designModel` แก้ได้แค่ที่ Profile, `privacy` มีแค่ที่ Project)
- **เส้นแดงรวมกันอย่างเดียว** ทุกชั้นเพิ่มได้ ไม่มีชั้นไหนลบเส้นแดงของชั้นบนได้ (และเส้นแดงในตัว §11.2 ลบไม่ได้เสมอ)
- หน้า "ค่าที่ใช้จริง" แสดงทุกค่า + มาจากชั้นไหน + ค่าของแต่ละชั้น (ค่าที่ถูกทับขีดฆ่า) + ปุ่มแก้ทับ/กลับไปใช้ค่าสืบทอด
- แก้ Process แล้วทุก Profile/Project ที่ใช้เปลี่ยนตาม ยกเว้นค่าที่แก้ทับไว้ — เปลี่ยน Process หรือเปลี่ยน Profile ของโปรเจคต้องให้คนยืนยัน (เป็นการเปลี่ยนกติกา)

### 25.3 โปรเจคส่วนตัว vs ทีม
| | ส่วนตัว | ทีม |
|---|---|---|
| ใครเห็น/อนุมัติ | เจ้าของคนเดียว | สมาชิกตามบทบาท (§19.2) |
| ความเป็นส่วนตัวเริ่มต้น | private | shared (เปลี่ยนได้) |
| บัญชี AI | บัญชีส่วนตัวของเจ้าของ | บัญชีที่โปรเจคอนุญาต (§24.4) |
| Board / claims | ของคนเดียว (กันงานซ้ำระหว่าง session ของตัวเอง) | ใช้ร่วมกันทั้งทีม (§20) |
| wiki ส่วนกลาง | `hpk-shared/users/<id>/` | `hpk-shared/team/` (ถ้าโปรเจค shared) |
| หน้าทีม | ไม่แสดง | แสดงสมาชิก/บทบาท/ผู้อนุมัติ |
- เปลี่ยนส่วนตัว → ทีมได้ (ต้องยืนยัน, เพิ่มสมาชิก); ทีม → ส่วนตัวต้องให้ owner ทุกคนยืนยัน
- ใช้ได้ทั้งเครื่องคนเดียว (โปรเจคส่วนตัว + ทีมบน server เดียวกันหรือคนละที่)

### 25.4 หน้าจอ
- **Process & profiles** (`#/setup`): แผนผัง Process → Profile → Project, รายการ Process, รายการ Profile, ค่าที่ใช้จริงของแต่ละโปรเจค
- **โปรเจค**: แยกส่วน "โปรเจคทีม" และ "โปรเจคส่วนตัว" แสดง Process › Profile ของแต่ละโปรเจค
- **เพิ่มโปรเจค**: มีขั้น "ประเภทและ profile" — เลือกส่วนตัว/ทีม, สมาชิก, Profile (พา Process มาด้วย)
- ตัวเลือกโปรเจคในแถบซ้ายจัดกลุ่มทีม/ส่วนตัว; เมนูทีมแสดงเฉพาะเมื่ออยู่ในโปรเจคทีม

### 25.5 ต้องตรวจใน M0
- Hermes สลับโปรไฟล์ต่อ session ได้ไหม (session ของโปรเจค A ใช้โปรไฟล์ X ขณะที่อีก session ใช้โปรไฟล์ Y พร้อมกัน)
- ส่ง `WIKI_PATH` / cwd ต่อ session ผ่าน ACP หรือ env ตอนเริ่มได้ไหม

## ภาคผนวก A — การย้ายโปรเจคเดิมเข้าระบบ (แนวทางทั่วไป)
